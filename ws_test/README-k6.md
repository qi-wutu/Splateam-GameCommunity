# WebSocket 压测说明（k6）

在 `ws_test/` 下的三个脚本，用于对后端 `GET /api/ws` 做单机并发压测。

| 文件 | 作用 |
|---|---|
| `gen-tokens.mjs` | 生成 N 个**独立 user_id** 的合法 JWT → `tokens.txt` |
| `ws-loadtest.js` | k6 脚本，两种模式：`conn`(连接数) / `throughput`(消息吞吐) |
| `run-k6.sh` | 一键运行：生成 token → 调 ulimit → 跑 k6 |

---

## 一、为什么需要"每个连接一个独立 token"

服务端 Hub [service/ws_service.go](../../service/ws_service.go) 的 `Register` 分支：

```go
if old, ok := h.Clients[client.UserID]; ok {
    close(old.Send)
    old.Conn.Close()
}
```

**同一个 `user_id` 再来一个连接，会直接把旧连接踢下线。** 所以如果你让所有 VU 共用同一个 token 开 N 个连接，第 2 个会把第 1 个挤掉，最终服务端看到的"在线"永远只有 1。**测出来的"并发数"是假的。**

解决：`gen-tokens.mjs` 给每个连接生成一个带独立 `user_id` 的 JWT。这些 user_id 不需要真的存在于数据库——chat 时 `GetUserByID` 查不到会 fallback 用 `user_id` 当昵称，逻辑照样跑通。

---

## 二、怎么跑

前置：装好 `k6` 和 `node`，服务器已启动（`go run .`），MySQL/Redis 可用。

先在一个终端启动服务器并保留日志（用于取"在线: N"峰值）：

```bash
go run . > server.log 2>&1 &
```

然后（在 `ws_test/` 下）：

### 模式一：并发连接数

```bash
MODE=conn CONNS=5000 DURATION=60s ./run-k6.sh
```

- k6 填满 `CONNS` 个 VU，每个 VU **保持一条连接整轮不断开**。
- 你要的"单机并发连接数" = **服务器日志里 `在线: N` 的最大值**：

```bash
grep -E '在线: ' server.log | grep -oE '[0-9]+' | sort -n | tail -1
```

> 用服务端日志而不是 k6 的 VU 数，因为那是服务端**真实同时持有**的连接数。k6 的 VU 数只是"尝试开多少条"。

### 模式二：消息吞吐

```bash
MODE=throughput TP_VUS=200 DURATION=60s PARTY_ID=1 SEND_INTERVAL_MS=200 ./run-k6.sh
```

- 所有 VU 加入同一个房间，每个 VU 每 `SEND_INTERVAL_MS` 发一条 chat。
- 看 k6 输出的 `ws_msgs_sent`（客户端发出）和 `ws_msgs_received`（客户端收到）。
- 注意到收会放大：一条消息广播给房间内所有成员（含发送者）。所以
  `ws_msgs_received ≈ ws_msgs_sent × 房间内连接数`（若无丢包）。**这是服务端真实的广播上限。**

## 三、跑完能诚实写进简历的说法

✅ **正确的说法（站得住）：**
> 用 k6 对 WebSocket 网关做单机压测，在单机部署、`ulimit`=xxx 条件下，稳定支撑 X 个并发长连接；在有 N 连接同时在线时，房间消息广播吞吐约 Y msg/s，超过后因服务端非阻塞丢包策略开始丢消息。

❌ **错误的说法（会翻车，别这么写）：**
> "模拟了真实生产流量 / 模拟了真实用户 / X 万并发。" —— 单机压测**不是**真实场景模拟，别贴"真实"标签。

### 为什么不是"真实场景"
1. **压测机若和服务器同一台**，k6 自己会抢 CPU/内存/文件句柄，数字代表"同机"表现，不是服务器纯上限。
2. **客户端也有上限**：每建一条 TCP 连接占一个文件句柄，`ulimit -n` 往往**先卡住压测机**，而不是服务器。所以"能开多少连接"可能反映的是客户端极限。
3. **真实用户不是"连上就不动"**：有随机进出、消息大小不一、网络抖动/延迟、DB/Redis/MQ 背压。压测只测连接天花板和广播路径。

要让数字更硬，把压测机放到**另一台机器**，并在简历上写清楚条件（硬件、系统、`ulimit`、连接数/消息数分别测）。

## 四、你代码里两个真实发现（面试能加分，也决定数字）

1. **按 user_id 去重踢连接**（`ws_service.go` Register 分支 + [controller_ws.go:37](../../controller/controller_ws.go)）——单个用户重复连接会顶掉旧的。真实用户场景这是"防重复登录"；压测场景则是必须每个连接一个独立 user_id，否则测不出并发。
2. **`BroadcastToRoom` 非阻塞丢包**（`ws_service.go` 里 `default:` 跳过）——客户端 `Send` 通道(容量 256)满时**静默丢消息**，不报错。这决定了吞吐上限：连得再快，超出发送能力就是丢。这值得在简历里讲成"我定位到服务端在缓冲满时会丢消息"，比单纯报个数字更有说服力。

---

## 五、如果你要更高的并发连接数

- 服务器端（Linux）：`ulimit -n 200000`，`sysctl net.core.somaxconn`、`fs.file-max` 调大。
- 压测端同样提升 `ulimit -n`，甚至可以**多台压测机**并行跑 k6。
- k6 本身的连接能力也受其进程 FD 限制；连接数上到几万时优先考虑**压测机与服务器分离**。

## 六、本机实测结果（Windows 11 / Go 1.26 / 单机，压测机与服务器同一台）

### 连接并发（用 ws_loadgen，速率受限地爬坡）
| 目标 | 握手成功 | 握手失败 | 峰值同时在线上 | 服务端日志 `在线` 峰值 |
|---|---|---|---|---|
| 3,000 | 3,000 | 0 | 3,000 | 3,000 |
| 10,000 | 10,000 | 0 | 10,000 | 10,000 |
| 20,000 | 20,000 | 0 | 19,999 | 20,000 |
| 30,000 | 30,000 | 0 | 29,999 | 30,000 |

> **结论：单机、渐进建立连接（500–1000 连接/秒）时，服务器稳支撑 30,000 条并发 WebSocket 连接，握手零失败。**
> 50,000 的尝试在压测端崩溃（Go runtime panic，资源耗尽），非服务器原因，故 30,000 为已验证的上限。

### 消息吞吐（用 k6，200 个发送者同房间广播）
- 入站聊天：约 **2,000 条/秒**（200 VU × 每 200ms 1 条）
- 广播投递：约 **247,000 条/秒**（每条消息广播给房间内 200 个成员，含回显）
- **~38% 广播被丢弃**——直接命中 `BroadcastToRoom` 的 `default:` 非阻塞丢包策略（客户端 Send 缓冲 256 满即丢）

### 关键失真点（必须如实说明，别当真实生产并发讲）
1. **Redis 处于降级（未启动）**：连接数测试不受影响；但**消息吞吐测试没有走 Redis 写路径**（`cacheMessageToRedis` 被跳过），真实开 Redis 后吞吐会低一些。
2. **MySQL 正常**：每条 chat 都触发一次 `GetUserByID`（用户不存在→快速回退），所以吞吐里含真实 DB 查询。
3. **压测机与服务器同一台**：二者抢 CPU/内存，数字是"单机同时扛压测+服务"的表现，比纯服务器略保守。
4. **突发批量连接会被 Windows 拒绝**：一次性 SYN 洪峰会溢出发送接受队列，约 700 条后开始 `ECONNREFUSED`；真实用户渐进接入不会这样。生产要高并发需调大 `somaxconn` 或前置负载均衡。
5. **JWT 密钥**：auth bug（`utils.InitJWT()` 未被调用导致空密钥）已修复，服务端现在用 `config/.env` 的 `JWT_SECRET` 签名/校验。`run-k6.sh` 会从该文件读取并传给 `gen-tokens.mjs`，生成与服务器一致的 token；否则握手会被拒绝。

> 简历上建议这么写（诚实且站得住）：
> "WebSocket 单机压测：在单机部署、渐进建连下支撑约 3 万条并发长连接（握手零失败）；200 客户端同房间广播时服务端约可投递 2.4w 万条/秒消息，并定位到广播缓冲满时服务端会静默丢包。"
