## 待修复（Bug / 技术债）

### 高优先级

#### [WS] 全局 Hub 单锁在高并发广播下成为串行化瓶颈

- **Issue**：[#1](https://github.com/qi-wutu/Splateam-GameCommunity/issues/1)
- **状态**：待修复
- **优先级**：高 —— 当前路由已上线，但人群房间（大型 Party）广播时锁竞争明显，会拖慢全局广播并带来消息丢失。

`service/ws_service.go` 用一个全局 `Hub`（单把 `sync.RWMutex`）统一管理所有在线连接与房间：

1. **全局唯一锁**：所有房间的广播、所有连接的增删都抢同一把锁，一个忙碌房间会拖慢其他房间。
2. **持锁遍历房间**：`BroadcastToRoom` 在 `RLock` 内遍历房间所有成员逐个 channel 发送后才释放锁，持锁时长 ∝ 房间人数 × 一次 channel 写。
3. **写者优先**：Go `RWMutex` 一旦有写者（批量连接/断开）在等待，后续所有读者（广播）都会被阻塞。

**实测影响**：单机可支撑约 3 万条并发长连接；但大量连接挤进同一房间高频互发消息时，非阻塞丢弃 + 单锁先暴露瓶颈——200 客户端同房间广播约 **24.7 万条/秒**，其中 **约 38% 被静默丢弃**（客户端 `Send` 缓冲 256 满即丢）。

**方向**（详见 issue #1）：

- 分片锁（按 `partyId`/`userID` 哈希分片，不同房间互不抢占）
- 锁内不阻塞（`RLock` 内只收集目标成员，解锁后再统一发送）
- 在线表改 `sync.Map` / 写时复制（读零锁）
- 跨节点改用 Redis Pub/Sub 分发房间消息，单 Hub 单锁转为多节点分发（推荐作为长期方案）
